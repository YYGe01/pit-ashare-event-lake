# 量化非结构化数据每日爬虫实施方案

> 创建日期：2026-05-12
> 目标：为 QDC 建立合规、可恢复、可审计的每日新增非结构化数据采集机制，先服务 Qlib 日频训练数据积累，不承担历史新闻回补。

## 1. 结论

爬虫机制可行，但第一阶段应只解决：

```text
每日新增公告
每日新增新闻标题/摘要/链接
官方 PDF 或 HTML 原文留档
标题级和正文级事件因子日频聚合
```

不在第一阶段承诺：

```text
补齐多年历史新闻
绕过登录、验证码、付费墙或强反爬
抓取社交平台隐私或登录内容
用免费新闻源直接判断新闻 alpha 是否长期有效
```

推荐方案：

```text
QDC crawler-lite
  -> source adapter
  -> crawl_task 控制表
  -> raw append-only 留档
  -> bronze 结构化快照
  -> silver 文档表
  -> factor_engine 日频聚合
  -> Qlib export 外部因子
```

短期不建议直接上完整 Scrapy 项目或 Playwright-first 架构。原因：

```text
当前需求是每日新增、低频、可审计，而不是海量历史抓取。
QDC 已有 DuckDB 控制面、raw/bronze/silver/gold 分层和 daily-pipeline。
先接官方公告源和少量公开新闻源，轻量 adapter 更容易控制数据契约。
Scrapy/Playwright 可作为后续 source adapter 的执行后端，而不是第一天就引入新运行体系。
```

## 2. 调研依据

本方案参考的业界常见实践和官方资料：

| 方向 | 资料 | 对本项目的启发 |
| --- | --- | --- |
| 爬虫框架架构 | Scrapy Architecture：`https://docs.scrapy.org/en/0.24/topics/architecture.html` | 业界常见抽象是 scheduler、downloader、spider、item pipeline 分层；QDC 可借鉴，不必完整引入。 |
| 礼貌抓取和限速 | Scrapy AutoThrottle：`https://docs.scrapy.org/en/master/topics/autothrottle.html` | 需要按 source 配置 delay、并发、失败退避，避免免费源被打挂或封禁。 |
| robots 标准 | RFC 9309 Robots Exclusion Protocol：`https://www.rfc-editor.org/rfc/rfc9309` | 每个 source 上线前应记录 robots/条款检查结果；项目策略应比 RFC 更保守。 |
| 动态页面处理 | Playwright Python Auto-waiting：`https://playwright.dev/python/docs/actionability` | JS 页面可用浏览器自动化兜底，但成本高、慢、脆弱，应作为 fallback。 |
| 非结构化数据投资使用 | CFA Institute NLP 与 alternative data：`https://www.cfainstitute.org/insights/articles/using-nlp-to-unlock-treasure-trove-of-alternative-data` | 文本、公告、新闻、社媒可产生投资洞察，但需要 NLP、可靠来源和专业判断。 |
| 另类数据风险 | Deloitte alternative data：`https://www2.deloitte.com/us/en/pages/financial-services/articles/infocus-adopting-alternative-data-investing.html` | 另类数据有 alpha 潜力，也有合规、质量、供应商和操作风险。 |
| 官方公告入口 | 巨潮资讯公告查询：`https://www.cninfo.com.cn/new/commonUrl/pageOfSearch?lastPage=index&url=disclosure%2Flist%2Fsearch` | 公告源比新闻源更适合作为第一阶段重点，且天然可按日期增量。 |

## 3. 业界常见方案汇总

### 3.1 授权数据源 / API 优先

机构量化通常优先使用：

```text
交易所 / 官方披露平台
商业新闻和公告 feed
授权历史新闻库
供应商清洗后的文本因子
```

优点：

```text
历史覆盖较完整
字段稳定
合规边界清晰
运维成本低
```

缺点：

```text
付费
个人研究成本高
对字段口径依赖供应商
```

本项目判断：

```text
后续验证策略有效后，再接 Tushare/JQData/Wind/Choice/商业新闻源补历史。
当前先用爬虫每天积累新增数据，避免长期等待历史源。
```

### 3.2 Scrapy 型通用爬虫框架

Scrapy 的常见架构是：

```text
Spider 生成请求和解析 item
Scheduler 管理请求队列
Downloader 下载页面
Middleware 处理请求/响应
Item Pipeline 清洗、去重和入库
```

优点：

```text
成熟
适合多源、多页面、分页和高吞吐抓取
有 AutoThrottle、Retry、Pipeline 等成熟能力
```

缺点：

```text
引入 Twisted 运行模型和新的项目结构
和当前 qdc CLI / DuckDB 控制面会有一层集成成本
对每日低频新增来说偏重
```

本项目判断：

```text
第一阶段不直接引入 Scrapy。
如果后续新闻源增加到 10 个以上，或者需要大规模分页抓取，再把部分 source adapter 迁移到 Scrapy backend。
```

### 3.3 轻量 requests/httpx + parser adapter

这是个人量化和小团队常用方式：

```text
每个 source 一个 adapter
requests/httpx 拉 JSON/HTML/PDF
BeautifulSoup/lxml/正则/表格解析
统一写 raw、bronze、silver
用 CLI 或系统计划任务调度
```

优点：

```text
简单
容易和当前 QDC 分层融合
低频每日增量足够
每个 source 的失败边界清晰
```

缺点：

```text
需要自己实现任务队列、限速、重试、监控
source 多了以后会膨胀
```

本项目判断：

```text
最适合当前阶段。
QDC 已有 backfill_task / dataset_watermark / source_object，可复用模式扩展 crawler_task。
```

### 3.4 Playwright / 浏览器自动化

适用于：

```text
页面强依赖 JavaScript
接口难以稳定复用
需要模拟点击、分页、动态加载
```

优点：

```text
能处理动态页面
调试直观
Playwright 有 auto-waiting 和定位器机制
```

缺点：

```text
慢
资源重
长期稳定性差于 HTTP API/HTML
容易被网站策略变化影响
```

本项目判断：

```text
只作为 fallback backend。
第一阶段禁止用 Playwright 绕过登录、验证码、付费墙或访问限制。
```

### 3.5 消息队列 / 分布式爬虫

大型机构常见：

```text
Kafka / RabbitMQ / Redis Queue
分布式 worker
对象存储
ElasticSearch / OpenSearch
数据湖表格式
统一监控告警
```

本项目判断：

```text
当前不需要。
个人本地 QDC 先用 DuckDB + 文件系统 + Windows 计划任务，避免过早运维复杂化。
```

## 4. 推荐架构：QDC crawler-lite

### 4.1 模块边界

新增目录建议：

```text

  models.py            统一 CrawlRequest / CrawlResult / ParsedDocument
  runner.py            执行任务、限速、重试、状态流
  robots.py            robots/条款检查记录
```

### 4.5 去重策略

公告：

```text
优先 source_record_id
其次 pdf_sha256
再次 source_id + instrument + publish_time + normalized_title
```

新闻：

```text
优先 canonical_url
其次 source_id + publish_time + normalized_title
再次 title_hash + media_name + instrument
```

同一文档映射多只股票时：

```text
文档实体只保留一份
映射关系单独进入 document_security_map
因子聚合按 instrument 展开
```

### 4.6 PIT 时间规则

必须保留：

```text
publish_time       来源显示发布时间
observed_at        本系统首次看到时间
collect_time       本次采集入库时间
effective_time     策略允许使用时间
effective_trade_date 交易日对齐结果
```

每日新增场景：

```text
observed_at 接近真实可见时间，可用于后续 PIT 训练。
收盘后采集的当日公告/新闻，默认 effective_trade_date 应至少对齐到下一个交易日，避免当日收盘前不可得信息污染。
```

## 5. Source 优先级

### P0：官方公告源

优先级最高：

```text
cninfo_announcement
sse_announcement
szse_announcement
bse_announcement
```

原因：

```text
公告是正式披露信息，合规价值高。
按日期增量天然适合每日采集。
PDF 和标题容易留档、hash 和去重。
对 Qlib 日频外部因子更稳定。
```

第一阶段建议先接：

```text
cninfo_announcement
```

巨潮是法定信息披露平台，公告查询页面可作为 source 入口。实现时应优先使用页面实际调用的公开 JSON 请求；如果接口变化，再回退 HTML 解析或人工维护。

### P1：交易所公告补源

用途：

```text
补 CNINFO 漏采
交叉校验公告标题、时间、PDF
标记 source_conflict / source_missing
```

注意：

```text
不要在第一阶段追求四个公告源同时完全接入。
先把 CNINFO 的 raw、PDF、去重、时间字段和质量报告做扎实。
```

### P2：公开新闻近实时补位

候选：

```text
东方财富个股新闻 / 快讯
新浪财经
同花顺公开快讯
财联社公开快讯
```

当前定位：

```text
只做每日新增。
优先标题、摘要、URL、来源、发布时间。
正文保存需要按 source copyright_policy 控制。
```

训练判断：

```text
可用于累计 daily_news_factor。
不可用于补历史。
不可直接判断新闻 alpha 长期有效。
```

### P3：社交舆情

第一阶段不建议做：

```text
股吧
雪球
微博
论坛
评论区
```

原因：

```text
登录和反爬边界复杂
噪声大
股票映射歧义高
版权和隐私风险更高
对个人本地量化项目的第一阶段收益不确定
```

## 7. 调度建议

当前每日行情流水线建议 18:30。非结构化数据建议拆成两个窗口：

```text
18:40  公告和新闻首次采集
21:30  公告和新闻二次补采
06:30  次日早间补采前一交易日遗漏
```

原因：

```text
公告和新闻有延迟发布。
晚间公告较多，单次 18:40 不一定完整。
次日早间补采可提升覆盖率。
```

Windows 计划任务示例：

```powershell
schtasks /Create /TN "QDC Crawl Daily 1840" /SC DAILY /ST 18:40 /TR "cmd /c cd /d E:\code\pit-ashare-event-lake && D:\Miniconda3\Scripts\conda.exe run -n ai-trader qdc crawl-daily >> data\quant_data_center\logs\crawl-daily.log 2>>&1"
schtasks /Create /TN "QDC Crawl Daily 2130" /SC DAILY /ST 21:30 /TR "cmd /c cd /d E:\code\pit-ashare-event-lake && D:\Miniconda3\Scripts\conda.exe run -n ai-trader qdc crawl-daily >> data\quant_data_center\logs\crawl-daily.log 2>>&1"
```

## 8. 质量规则

Source 级质量：

```text
HTTP 成功率
解析成功率
空结果率
重复率
PDF 下载成功率
字段漂移
响应大小异常
```

数据级质量：

```text
publish_time 缺失
instrument 缺失
title 缺失
URL 缺失
PDF hash 重复但标题冲突
同一公告多源标题不一致
公告发布时间晚于 collect_time
effective_trade_date 无法对齐
```

因子级质量：

```text
每日公告数量突变
每日新闻数量突变
全市场文档数为 0
单一来源连续失败
某标的文档数异常高
```

## 9. 因子设计

Qlib 不直接消费 raw 文本。爬虫产物进入 Qlib 前只输出日频稳定字段。

公告因子：

```text
announcement_count
announcement_risk_count
announcement_financing_count
announcement_operation_count
announcement_regulatory_count
announcement_litigation_count
announcement_performance_count
announcement_correction_count
announcement_pdf_count
announcement_late_night_count
```

新闻因子：

```text
news_count
news_positive_count
news_negative_count
news_risk_count
news_growth_count
news_financing_count
news_media_count
news_source_count
news_confidence_weighted_count
```

后续正文 NLP：

```text
先用规则分类。
再用本地或 API LLM 做小样本验证。
全量 LLM 打标必须记录 prompt_version、model、temperature、输入 hash、输出 hash。
```

## 10. 合规和安全边界

项目级规则：

```text
不绕过登录、验证码、付费墙。
不抓取需要授权的付费正文。
不保存 cookie、token、账号密码。
不使用高并发压测式抓取。
尊重 robots 和网站条款；无法判断时标记 manual_review_required。
对版权不明确的新闻正文，默认 metadata_only，只保存标题、摘要、URL、来源和 hash。
```

技术默认值：

```text
每个 source 单并发起步。
min_delay_seconds >= 3。
失败指数退避。
HTTP 429 / 403 立即降速并暂停该 source。
User-Agent 标明个人研究用途和联系方式占位。
```

## 12. 推荐执行顺序

当前最适合本项目的下一步：

```text
1. 实现 crawler_source / crawl_task / crawl_run 控制表。
2. 实现 qdc crawl-plan / crawl-run / crawl-daily control-only。
3. 接 cninfo_announcement，每天抓新增公告和 PDF hash。
4. 把 CNINFO 公告接入 daily_announcement_factor。
5. 再接 1 个公开新闻源做每日新增补位。
6. 连续运行 20 个交易日后，根据覆盖和训练效果决定是否接付费历史源。
```

第一阶段成功标准：

```text
每天自动跑完，无需人工干预。
所有 raw 可追溯。
公告 PDF hash 可复查。
解析失败不会阻塞行情 daily-pipeline。
质量报告能发现空采、字段漂移和重复。
Qlib provider 中能看到稳定公告日频因子。
```
