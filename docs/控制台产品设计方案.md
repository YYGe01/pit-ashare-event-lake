# 控制台产品设计方案

> 目标：让第一次接触项目的人也能通过 `qdc console` 判断数据采集是否正常、哪里卡住、下一步该做什么。

## 1. 设计原则

控制台不是给模型训练用的研究页面，而是给数据工程和回补监控用的操作观察台。页面信息必须先回答问题，再展示明细。

核心原则：

```text
先结论，后明细
先中文解释，后保留英文代码名
先状态和下一步，再给底层表格
只读页面不提供隐式写操作
默认展示少量关键数据，复杂明细通过筛选下钻
```

## 2. 信息架构

当前最佳方案是混合视角，而不是只按 dataset 或只按标的展示：

```text
总览             -> 我现在能不能放心让回补继续跑
回补任务         -> 哪个数据集、哪段日期、哪批标的卡住
数据预览         -> 某个表里的研究数据长什么样
质量检查         -> 哪些数据异常还没处理
Qlib 导出        -> 研究数据是否已经导成 Qlib provider
后续标的画像      -> 某只股票在所有日期上的行情、新闻、公告、因子时间线
```

为什么不是只按标的展示：

```text
回补和质量排障需要 dataset / task 视角，否则很难知道 daily_bar、news、announcement 哪条链路卡住。
研究验证需要标的视角，因为你关心某只股票每天的行情、新闻、公告和因子是否对齐。
所以控制台首页和排障页保持 dataset/task 视角，后续单独增加“标的画像”页做研究下钻。
```

## 3. 总览页

总览页只回答一个问题：当前数据采集是不是在正常推进。

页面结构：

```text
页面摘要
  说明这个页面用来判断当前采集是否正常

先看这三件事
  采集是否卡住
  数据覆盖到哪里
  Qlib 是否可用

关键指标
  统一研究层行数
  回补任务
  运行记录
  阻塞任务
  源文件索引
  水位记录
  Qlib 导出
  质量问题

数据维度覆盖
  每个数据集的行数、数据源、日期范围、覆盖标的数
  核心日频维度的理论应有行数、已覆盖行数和缺失行数
  新闻、公告、停牌状态等稀疏维度只展示有记录的覆盖，不把没有事件直接判为缺失

标的核心完整度
  以参考标的集合和交易日历形成检查网格
  核心维度先按 daily_bar、adj_factor、price_limit 判定
  显示完整标的数、缺失标的数、每个维度缺失了多少标的
  明细表列出每个缺失标的缺哪些维度

采集进度
  每张卡 = 一个 dataset + source_id + universe 的任务组
  显示完成率、日期范围、成功、待执行、运行中、失败
  给出下一步建议

任务状态 / 数据水位 / 最近运行
  给排障者看更细明细
```

采集进度的状态解释：

```text
complete  全部任务成功，可以继续 build-factors / sync-parquet / export-qlib
running   正在运行，正常观察即可
pending   已排队，等待 run-backfill 消费
blocked   有 failed 或 stale running，需要先处理
failed    任务失败，查看 last_error 后重试
```

### 3.1 覆盖统计口径

参考标的优先级：

```text
1. 最新 universe_constituent 成分
2. config/quant_data_center.yaml 里的 universes 配置
3. silver 表里已有 instrument 的并集
```

参考交易日优先级：

```text
1. trade_calendar 里的开市日
2. daily_bar / adj_factor / price_limit 的交易日并集
```

核心完整度当前只判定：

```text
daily_bar     日线行情
adj_factor    复权因子
price_limit   涨跌停价格
```

原因是这三个维度对 Qlib 日频研究最接近“每个标的每个交易日都应该有”。`news`、`announcement`、`trade_status`、`daily_news_factor`、`daily_announcement_factor` 都可能天然稀疏：没有新闻、没有公告或没有停牌，不等于数据缺失。

## 4. 回补任务页

这个页面用于定位采集队列里的具体任务。

新手优先看：

```text
status       当前任务状态
dataset      哪类数据，例如 daily_bar、news、announcement
start/end    这条任务负责的日期范围
symbols      这条任务负责的标的批次
last_error   失败原因
updated_at   最近更新时间
```

处理建议：

```bash
qdc recover-running --dataset <dataset> --older-than-minutes 15
qdc split-backfill --task-id <task_id> --batch-size 10
qdc run-backfill --dataset <dataset> --retry-failed
```

## 5. 数据预览页

这个页面按标的查看数据，不再以“随便选一张表”为主入口。页面顶部提供可搜索下拉框，支持输入 `SH600000`、`600000`、股票名称或行业后选择标的。页面分成两种视角：

```text
原始数据预览：读取 qdc_meta.source_object 登记的 raw JSON，尽量按上游原字段展示“采集到了什么”
处理后因子预览：读取 qdc_silver 里已经按交易日和标的对齐的研究字段
```

操作顺序：

```text
1. 在标的搜索框输入代码、名称或行业，从下拉里选择 instrument
2. 输入开始和结束日期，避免一次拉太多行
3. 切换“原始数据预览”或“处理后因子预览”
```

原始数据预览的典型用途：

```text
daily_bar / adj_factor / price_limit / trade_status  看 AkShare 当时返回了哪些原始字段
news / announcement                                看上游返回的标题、链接和发布时间
raw 文件索引                                      看 source_id、上游函数、采集参数和错误信息
```

处理后因子预览的输出：

```text
顶部摘要：交易日数量、核心完整天数、新闻明细条数、公告明细条数
行情价格：open、high、low、close、pre_close、volume、amount、vwap
复权和交易限制：adj_factor、limit_up/down、prev_close、limit_rule、trade_status、halt_reason
新闻因子拆解：news_count、sentiment、正负面计数、增长/风险/融资/合同/回购/监管/诉讼/业绩等事件计数
公告因子拆解：announcement_count、sentiment、正负面计数、增长/风险/融资/经营/合同/回购/监管/诉讼/业绩等事件计数
明细列表：同一筛选范围内的 news 和 announcement 标题、发布日期和来源
```

接口边界：

```text
/api/instruments              负责标的下拉搜索
/api/raw-instrument-preview   负责按 instrument 读取 raw JSON 原始采集记录
/api/factor-preview           负责按 instrument 合并多个日频表和文本明细
/api/dataset-preview          保留为兼容接口，不再作为前端主入口
```

## 6. 质量检查页

这个页面用于处理数据异常。

优先级：

```text
open 且 severity 高的问题优先处理
closed 只作历史记录
message 是给人的说明，entity_key 通常指向具体标的或日期
```

## 7. Qlib 导出页

这个页面用于确认 QDC 数据是否已经交给 Qlib。

判断顺序：

```text
最近导出是否 success
导出的日期范围是否覆盖研究区间
provider_uri 是否是预期目录
导出文件是否登记到 source_object
最后执行 qdc verify-qlib 验证 Qlib 可读
```

## 8. 后续标的画像页

后续应新增“标的画像”页，作为研究验证视角。

推荐交互：

```text
输入标的 + 日期范围
顶部显示该标的覆盖天数、最早/最晚交易日、新闻/公告数量
主时间线按 trade_date 展示行情、交易状态、新闻因子、公告因子
点击某天展开当天新闻标题、公告标题和事件标签
默认只加载最近 250 个交易日，更多历史分页或按日期筛选
```

这个页面不替代总览和回补任务页，因为标的视角看不出整个 dataset 的采集队列是否健康。
