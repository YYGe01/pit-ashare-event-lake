# quant_data_center 改造实施文档

> 创建日期：2026-05-11
> 当前状态：项目骨架和主链路已落地，当前执行中心是每日数据采集验证。
> 目标：把当前仓库改造成个人量化统一数据中心 `quant_data_center`，服务 Qlib 研究。

> 2026-05-12 口径更新：当前执行中心切到每日数据采集。历史回补保留为已有能力，但先冻结，不再作为默认开发、运行或控制台展示重点。

## 1. 改造结论

当前项目主线是个人量化统一数据中心：

```text
quant_data_center
  -> 数据采集
  -> 每日增量
  -> 标准化清洗
  -> 稳定日频因子加工
  -> 导出 Qlib 可读数据
```

当前默认推进顺序是每日采集优先：

```text
daily-pipeline / crawl-daily
  -> raw / bronze / silver
  -> build-factors
  -> sync-parquet
  -> quality
  -> export-qlib
  -> console 观察
```

冻结边界：

```text
历史回补、训练级历史底座补齐、回补队列消费和回补控制台展示先不推进。
除非用户明确要求解冻，否则不主动执行 plan-backfill / run-backfill 或新增回补能力。
```

不在本项目里做：

```text
模型训练
Qlib qrun 实验配置管理
组合回测
实盘下单
东方财富/掘金终端适配
```

后续边界：

```text
当前仓库                          -> quant_data_center
/root/code/qlib                   -> Qlib 框架源码，尽量不改
/root/code/quant_research          -> 后续再建，放实验、模型、回测、target_weight
/root/code/quant_live_trading      -> 更后面再建，放终端执行和对账
```

第一阶段先不新建 `quant_research`，避免在采集、因子、研究都未稳定时拆太多项目。

环境口径：

```text
conda 运行环境统一使用已存在的 ai-trader
不要新建 quant-data-center conda 环境
quant-data-center 仅保留为 Python 项目发行名
```

## 2. 为什么要大改

当前项目已有价值：

```text
已有 connector 和 normalize 经验
已有 raw 落盘和质量检查基础
已验证 AkShare 数据源入口和基础 normalize 经验
```

但当前核心存储偏采集审计账本：

```text
crawl_run
raw_object
raw_item_version
quality_check_result
collection_manifest
source_health
lineage_event
```

这些表对严肃数据湖有用，但对个人 Qlib 研究不够直接。Qlib 研究优先需要：

```text
stock_basic
trade_calendar
daily_bar
adj_factor
price_limit
trade_status
announcement
news
daily_news_factor
daily_announcement_factor
qlib export
```

因此本次迁移不追求兼容此前的 CLI、manifest 和 metadata 账本。当前主线按 QDC 模块重新实现。

## 3. 目标分层

数据分四层：

```text
raw
  保存上游原始响应、下载文件和关键请求 metadata，只作证据与重算来源。

bronze
  provider 原始结构化结果，字段尽量贴近上游。

silver
  统一口径研究表，统一股票代码、日期、字段名和去重规则。

gold
  Qlib/模型可直接消费的日频因子表。
```

推荐目录：

```text
data/
└── quant_data_center/
    ├── qdc.duckdb
    ├── raw/
    ├── parquet/
    │   ├── bronze/
    │   ├── silver/
    │   └── gold/
    ├── qlib/
    └── logs/
```

代码目录目标：

```text
src/quant_data_center/
├── cli.py
├── collectors/
├── normalizers/
├── storage/
├── jobs/
├── factor_engine/
├── qlib_export/
└── quality/
```

## 4. 存储选择

第一版使用：

```text
DuckDB + Parquet
```

暂不上 PostgreSQL。原因：

```text
个人维护成本低
适合本地批量分析
适合和 Pandas/Polars/Qlib 导出衔接
不需要维护数据库服务
```

DuckDB 存控制表、小维表和视图；Parquet 存行情、公告、新闻、因子等大表。

## 5. 控制表设计

先建立最小控制表：

```text
job_run
  每次 backfill/daily/build_factors/export_qlib/smoke 的运行记录。

backfill_task
  可恢复的历史回补任务分片。

dataset_watermark
  每个 dataset/source/universe 的完成水位。

source_object
  raw 文件索引，替代旧 raw_object。

quality_issue
  缺失、重复、异常值、字段漂移等质量问题。
```

这些表用于调度和可恢复运行，不再复刻旧的复杂 manifest/lineage 体系。

## 7. 时间口径

文本类数据必须保留多个时间字段：

```text
publish_time       来源显示发布时间
arrive_time        理论上你能看到的时间
arrive_time_quality observed / estimated / unknown
collect_time       本系统采集入库时间
effective_time     因子允许使用的时间
```

历史回补新闻通常无法证明真实 `arrive_time`，不能伪装成当年已经看到。规则：

```text
is_backfill = true
collect_time = 实际采集时间
arrive_time_quality = estimated 或 unknown
effective_time = 保守规则估算
```

公告、新闻、财务披露进入因子前，都必须经过交易日历对齐。时间对齐逻辑集中放在：

```text
src/quant_data_center/factor_engine/calendar_align.py
```

不要散落在 connector 或 Qlib YAML 里。

## 8. 历史回补设计

当前状态：冻结。以下内容保留为已经实现和后续可能恢复的架构设计，不作为当前默认工作项。

历史回补不能只是 `start_date/end_date` 循环。目标流程：

```text
qdc plan-backfill
  -> 生成 backfill_task：dataset + source + date_range + symbol_batch

qdc run-backfill
  -> 逐个 task 拉数据
  -> 写 raw
  -> 写 bronze
  -> merge 到 silver
  -> 更新 task 状态和 dataset_watermark

qdc daily
  -> 本质上是 date_range=单日的 backfill
  -> 走同一套 normalizer 和 writer
```

回补和每日增量必须走同一套 writer：

```text
collect -> raw -> bronze -> normalize -> silver -> factor_engine -> gold
```

区别只在：

```text
job_type = backfill / daily
is_backfill = true / false
```

## 9. factor_engine 放置原则

第一阶段 `factor_engine` 放在当前项目，也就是：

```text
src/quant_data_center/factor_engine/
```

原因：

```text
因子加工依赖原始表、清洗表、交易日历、股票映射
稳定因子应该可重算、可版本化、可导出
它是数据中心的一部分，不是 Qlib 框架源码的一部分
```

Qlib 项目只负责模型训练、回测、预测、分析。`/root/code/qlib` 里可以保留少量自定义 handler 示例，但不要承载采集、清洗、新闻去重、LLM 打标和历史回补。

## 10. Qlib 接入

Qlib 不直接读新闻正文，也不直接读 DuckDB 控制表。目标流程：

```text
silver/gold Parquet
  -> qdc export-qlib
  -> Qlib provider_uri
  -> qrun / DatasetH / Alpha158 / 自定义 handler
```

导出字段示例：

```text
open
high
low
close
volume
amount
factor
news_count_1d
news_sentiment_mean
news_risk_count
sentiment_mean_3d
announcement_penalty_60d
```

Qlib 侧职责：

```text
基础行情字段 -> Alpha158/Alpha360
外部稳定因子字段 -> 自定义 handler 追加
模型训练/回测 -> Qlib
```

```text
qdc run-backfill --retry-failed

qdc run-backfill 真实 AkShare 分支：announcement / news
qdc refresh-universe / list-universe
qdc daily
qdc daily-pipeline
qdc_silver.stock_basic / universe_constituent / trade_calendar / daily_bar / adj_factor / price_limit / trade_status / announcement / news / daily_news_factor / daily_announcement_factor schema

AkShare 阶段 2 回补写 raw JSON、bronze Parquet，并登记 qdc_meta.source_object

qdc verify-qlib 使用本地 Qlib 读取导出的 provider
```

`run-backfill --control-only` 只用于验证任务状态流和水位表，不采集真实数据。默认 `run-backfill` 只运行 `pending` 任务；需要人工恢复失败任务时，使用 `run-backfill --retry-failed` 显式运行 `failed` 任务。当前 `run-backfill` 已支持 AkShare 的 `stock_basic`、`trade_calendar`、`daily_bar`、`adj_factor`、`price_limit`、`trade_status`、`announcement`、`news`；其他 dataset/source 会在 `plan-backfill` 或 `run-backfill` 阶段明确拒绝。

`daily_bar`、`adj_factor`、`price_limit`、`news` 可从 `qdc_silver.universe_constituent` 最新快照或配置里的静态 `--universe` 展开 symbol，也可以显式传入 `--symbols` 覆盖。当前已经支持 AkShare 指数成分快照刷新；历史成分变更追溯可作为后续增强。

DuckDB 当前按单写进程使用；不要并行执行多个会写同一个 `qdc.duckdb` 的命令。`qdc console` 可以作为观察面和采集同时打开，也可以从今日总览启动一个受限的本地 `daily-pipeline --watch` 子进程；控制台会限制同一会话一次只跑一个流水线，并提供停止当前子进程的按钮。写入端会对瞬时 DuckDB 锁做等待重试，控制台 API 遇到采集写锁时返回“写入中”降级状态并继续刷新。

当前 `qdc_silver` 仍先落 DuckDB 表，作为真实 collector 迁移时的标准写入目标；AkShare 阶段 2 collector 已写入 raw JSON 和 bronze Parquet，`sync-parquet` 可从 DuckDB 派生 silver/gold Parquet 文件。

```bash
qdc console --host 127.0.0.1 --port 8765
```

实现范围：

```text
后端：src/quant_data_center/console.py，使用标准库 HTTP server、DuckDB read_only 查询和受限 daily-pipeline 子进程执行器；写锁期间返回 busy 降级 payload

API：daily-collection-status / daily-pipeline-run / daily-wide-preview / instruments / source-object-file，以及保留的 overview / quality-issues / source-objects / dataset-preview
页面：今日总览、数据预览
产品设计：今日总览先回答“今天能不能用”，再按采集进度、质量、供应商、覆盖和问题标的逐层下钻；英文术语尽量附中文
边界：页面只提供每日流水线启动/停止入口，不接收任意 shell 命令；同一控制台会话只允许一个 `daily-pipeline` 子进程运行；停止后如果控制表留下陈旧 `running` 批次，需要先恢复 running 任务再重试；历史回补队列不在控制台触发
```

数据覆盖口径：

```text
总览页保留今日结论、核心完整率、执行每日采集、采集路线图、质量体检、供应商采集质量、数据集覆盖、批次明细和问题标的。
data_coverage 统计展示在数据预览页“覆盖情况”tab：每个采集源表的行数、数据源、日期范围、覆盖标的数。
按标的覆盖明细像处理后因子宽表一样展开原始源字段列：行情价格 `open/high/low/close/pre_close/volume/amount/vwap`，涨跌和流动性 `turnover_rate/outstanding_share`，复权和涨跌停 `adj_factor/factor_type/raw_close/qfq_close/limit_up/limit_down/prev_close/limit_rule`，停复牌状态 `trade_status/halt_reason/halt_start_date/halt_end_date/halt_period/expected_resume_date/market`，事件明细 `news_count/announcement_count`。`change/pct_change/amplitude` 等可由价格推导且当前主采集链路不稳定提供的字段不进入原始宽表。
news、announcement、trade_status 当前没有稳定分母，只统计已有记录或天数，不把没有事件判成缺失。
daily_news_factor、daily_announcement_factor 属于处理后因子，只在处理后因子预览展示，不进入覆盖缺失总览。
```

数据预览页改造：

```text
数据预览页使用“覆盖情况 / 原始数据预览 / 处理后因子预览”三个 tab；覆盖情况 tab 合并展示源表覆盖和按标的原始源字段覆盖。
dataset-preview 保留为兼容接口，不再作为前端主入口。
instrument-timeline / factor-preview 按标的合并 daily_bar、adj_factor、price_limit、trade_status、daily_news_factor、daily_announcement_factor，并返回可按交易日展开的 news/announcement 明细。
当前前端主入口已调整为按标的搜索预览：/api/instruments 提供可搜索下拉，前端可连续添加多个标的；/api/raw-instrument-preview 展示按日期聚合的原始数据宽表，/api/factor-preview 展示处理后的日频因子宽表。
原始数据预览一行一个日期，横向展示日线行情、复权、涨跌停、交易状态等全部原始源字段；新闻和公告只显示数量，点击数量展开当天明细。
处理后因子预览中的 news_count / announcement_count 默认只展示数量，点击数量展开当天新闻或公告详情；带 Qlib 标记的字段会写入 `qdc export-qlib` 的 features，来源追踪、规则说明和停牌说明列只用于排查。
数据量较大的通用表格默认每页展示 5 行并提供客户端翻页；处理后因子宽表继续使用服务端 offset 分页。
```

长时间回补辅助命令：

```bash
qdc recover-running --dataset daily_bar --older-than-minutes 15
qdc split-backfill --task-id <task_id> --batch-size 10
```

说明：

```text
recover-running 用于把陈旧 running task 标记为 failed，后续可用 --retry-failed 重试。
split-backfill 用于把过大的 symbol 批次拆成更小 pending 子任务，原任务标记为 superseded。
控制台进度聚合会排除 superseded 任务，避免重复计入完成率。
```

设计取舍：

```text
先解决使用者可观察性：当前回补结果、每日任务状态、silver 数据和 Qlib 导出是否可见。
暂不引入 Airflow/Prefect/Dagster 这类调度平台，避免在数据契约未完全稳定前增加运维面。
后续如果需要操作能力，再在 console 中显式增加 plan / run / retry / export 按钮，并保留确认和审计记录。
```
