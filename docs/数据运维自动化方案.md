# QDC 数据运维自动化方案

> 创建日期：2026-05-15
> 当前结论：需要补齐自动化闭环，但第一阶段不建议把主采集放进 GitHub Actions；应让云服务器或本机定时任务执行采集和质量检查，失败后自动生成可交给 Codex 处理的 GitHub Issue。

## 1. 评估结论

用户提到的四层思路基本适合本项目：

```text
第 1 层：采集层
第 2 层：数据质量检查层
第 3 层：异常工单层
第 4 层：修复策略层
```

QDC 当前已经有第 1 层和第 2 层的基础能力：

```text
qdc crawl-daily
qdc build-factors
qdc sync-parquet
qdc quality
qdc_meta.quality_issue
console 质量展示
```

缺口主要在第 3 层和第 4 层：

```text
质量失败后没有稳定生成 GitHub Issue 的入口。
Issue 中没有统一的问题摘要、样例、修复检查清单。
Codex 处理质量工单时没有固定判断规则，容易把临时源站波动误改成永久代码，或把永久解析 bug 当成重跑解决。
```

本轮补齐了第一版闭环：

```text
qdc quality-issue-report
scripts/run_qdc_data_health.ps1
.codex/skills/data-ops/SKILL.md
```

## 2. 推荐运行闭环

第一阶段仍以本地或云服务器常驻运行为主，不把 GitHub Actions 当成主采集环境。

默认每日流程：

```powershell
conda run -n ai-trader qdc crawl-daily --date <target_date>
conda run -n ai-trader qdc build-factors --factor-set all --start <target_date> --end <target_date>
conda run -n ai-trader qdc sync-parquet --layer all
conda run -n ai-trader qdc quality --start <target_date> --end <target_date>
```

当质量检查失败时生成报告：

```powershell
conda run -n ai-trader qdc quality-issue-report --start <target_date> --end <target_date> --output data/quant_data_center/logs/quality-issue-<target_date>.md
```

报告会汇总：

```text
影响 dataset / issue_type / severity / count
最多 20 条样例 issue
建议 Codex 使用的修复规则
关闭前必须运行的验证命令
```

## 3. 自动 Issue 层

本仓库提供 PowerShell 脚本作为第一版自动化入口：

```powershell
scripts/run_qdc_data_health.ps1 -TargetDate 2026-05-14
```

默认行为：

```text
串行运行 crawl-daily、build-factors、sync-parquet、quality。
如果 quality 失败，写出 data/quant_data_center/logs/quality-issue-YYYY-MM-DD.md。
默认不创建 GitHub Issue，避免误把本地 smoke 失败刷到远端。
```

启用 GitHub Issue 创建：

```powershell
$env:QDC_CREATE_GITHUB_ISSUE = "1"
scripts/run_qdc_data_health.ps1 -TargetDate 2026-05-14
```

或：

```powershell
scripts/run_qdc_data_health.ps1 -TargetDate 2026-05-14 -CreateGitHubIssue
```

前提：

```text
本机或云服务器已安装并登录 GitHub CLI：gh auth login。
当前目录是目标 GitHub repo。
GitHub label 可不存在；若仓库未创建 label，gh issue create 可能失败，需要先在仓库创建 data-quality 和 qdc label，或通过 -IssueLabels 传已有 label。
不要把 GitHub token 写入仓库、Markdown 或配置文件。
```

脚本会用标题 `[QDC] Data quality failure: <target_date>` 搜索同名 open Issue，避免同一天重复开单。

## 4. Codex 修复策略层

固定规则放在：

```text
.codex/skills/data-ops/SKILL.md
```

处理质量 Issue 或相关 PR 时，Codex 应先分类：

```text
upstream_data_or_network
config_or_schedule
parser_or_schema_drift
factor_logic_bug
local_environment
manual_data_repair
```

核心判断：

```text
临时上游波动：重跑、记录源级观察，不急着改代码。
配置或调度错误：改配置、脚本、README 或实施计划。
解析/schema/因子 bug：做永久代码修复，并补测试。
本地环境问题：修环境或串行化运行，不硬编码业务绕行。
数据修复：必须有 raw 证据，不伪造 collect_time / observed_at。
```

## 5. 后续演进

当前第一版已经能让系统在质量失败后“说清楚哪里坏了”，但还不是最终形态。后续可以按风险逐步增强：

```text
1. quality_issue 去重和自动关闭：同一 dataset + issue_type + entity_key 重复失败不重复刷屏；修复后自动标记 resolved。
2. 源级 SLA：每个 source_id 记录成功率、空页率、解析拒绝率、date_scan_complete 和耗时分位数。
3. 质量规则分级：error 阻断导出，warning 只开观察单。
4. Qlib provider 联动：quality 同时检查外部 provider 最新日历和必需字段。
5. 控制台操作：从质量卡片直接打开报告或复制 Issue 创建命令。
6. 失败恢复 playbook：按 source_id 写固定重跑命令和可接受降级策略。
```

这些增强不需要一次做完。当前优先保证质量失败能稳定进入可追踪工单，并让后续 Codex 修复有固定边界。
