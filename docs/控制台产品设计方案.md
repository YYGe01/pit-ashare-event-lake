# 控制台产品设计方案

> 目标：让第一次接触项目的人也能通过 `qdc console` 判断 Qlib 基础 provider 是否可用、非结构化采集是否正常、外部因子是否构建完成、哪里卡住、下一步该做什么。
> 2026-05-14 口径更新：控制台主视角从“结构化回补监控”调整为“Qlib provider + 文档因子观察面”。历史回补和 `daily-pipeline` 任务只作为诊断视图保留。

## 1. 设计原则

控制台不是给模型训练用的研究页面，而是给数据工程和每日采集观察用的操作台。页面信息必须先回答问题，再展示明细。

核心原则：

```text
先结论，后明细
先中文解释，后保留英文代码名
先状态和下一步，再给底层表格
只读页面不提供隐式写操作
默认展示少量关键数据，复杂明细通过筛选下钻
```

## 2. 信息架构

当前最佳方案是混合视角，而不是只按 dataset 或只按标的展示：

```text
总览             -> Qlib provider、公告/新闻采集、外部因子是否正常
文档采集         -> 哪个 source_id、哪天、哪个文档源卡住
历史任务         -> 兼容查看回补和 daily-pipeline 诊断任务
数据预览         -> 文档、事件和外部因子长什么样
质量检查         -> 哪些数据异常还没处理
Qlib 接入        -> provider_uri 是否新鲜，external factors 是否可被 handler 读取
后续标的画像      -> 某只股票在所有日期上的公告、新闻、外部因子和 Qlib 基础字段时间线
```

为什么不是只按标的展示：

```text
文档采集和质量排障需要 source_id / dataset / task 视角，否则很难知道 cninfo_announcement、sse_announcement、eastmoney_roll_news 哪条链路卡住。
研究验证需要标的视角，因为你关心某只股票每天的公告、新闻、事件因子是否和 Qlib 交易日历对齐。
所以控制台首页保持 provider/source/factor 视角，后续单独增加“标的画像”页做研究下钻。
```

## 3. 总览页

总览页只回答一个问题：今天是否具备“Qlib 基础数据可用 + QDC 外部因子可用”的条件。

页面结构：

```text
页面摘要
  说明这个页面用来判断 Qlib provider、文档采集和外部因子是否正常

先看这三件事
  Qlib provider 是否新鲜
  公告/新闻采集是否卡住
  外部因子是否已经构建

关键指标
  Qlib provider 最新交易日
  公告行数
  新闻行数
  外部因子行数
  运行记录
  阻塞 source_id
  源文件索引
  水位记录
  质量问题

采集进度
  每张卡 = 一个文档源或因子任务
  显示日期范围、成功、待执行、运行中、失败、解析拒绝
  给出下一步建议

Qlib provider / 文档源状态 / 因子状态 / 最近运行
  给排障者看更细明细
```

采集进度的状态解释：

```text
complete  文档采集和因子构建成功，可以继续 Qlib handler 验证
running   正在运行，正常观察即可
pending   已排队，等待 crawl-run 或每日调度消费
blocked   有 failed 或 stale running，需要先处理
failed    任务失败，查看 last_error 后重试
```

覆盖统计和缺失分析不放在总览页。总览页只保留 Qlib provider 状态、文档源健康、外部因子状态、水位和最近运行，避免把“系统是否在跑”和“训练数据是否完整”混在同一屏。

## 4. 文档采集和历史任务页

默认页面用于定位文档采集任务；历史回补任务保留为诊断子页，不作为首页核心。

新手优先看：

```text
status       当前任务状态
dataset      哪类数据，例如 announcement、news、research_report
source_id    文档源，例如 cninfo_announcement、sse_announcement、eastmoney_roll_news
start/end    这条任务负责的日期范围
symbols      这条任务负责的标的批次；文档源为空时代表按日期或全源采集
last_error   失败原因
updated_at   最近更新时间
```

文档任务处理建议：

```bash
qdc crawl-daily --date <date> --source-id <source_id> --page-size 20 --max-pages 1 --skip-pdf-download
qdc crawl-recover-running --older-than-minutes 15
qdc crawl-list --source-id <source_id>
```

历史结构化诊断命令只放在折叠区域：

```bash
qdc recover-running --dataset <dataset> --older-than-minutes 15
qdc split-backfill --task-id <task_id> --batch-size 10
qdc run-backfill --dataset <dataset> --retry-failed
```

## 5. 数据预览页

这个页面负责回答“已经采到的文档、事件和外部因子长什么样，是否能和 Qlib 交易日历对齐”。页面通过三个分段 tab 展示覆盖统计、原始文档和处理后因子；原始文档和处理后因子 tab 顶部提供可搜索下拉框，支持输入 `SH600000`、`600000`、股票名称或行业后选择标的。处理后因子预览可以连续添加多个标的，按日期倒序、标的升序排开对比；原始文档预览只使用当前选择列表里的第一个标的。

```text
数据覆盖：合并展示 Qlib provider 最新交易日、文档源表行数、映射标的数和 external factor 对齐状态
原始文档预览：读取 qdc_meta.source_object 和 silver 文档表，展示后续因子加工会用到的标题、发布时间、URL、来源
处理后因子预览：读取 qdc_silver/gold 里已经按交易日和标的对齐的 external factors，用一张宽表展示
```

### 5.1 覆盖统计口径

参考标的优先级：

```text
1. 最新 universe_constituent 成分
2. config/quant_data_center.yaml 里的 universes 配置
3. silver 表里已有 instrument 的并集
```

参考交易日优先级：

```text
1. Qlib provider 的 calendars/day.txt
2. QDC trade_calendar 诊断表
3. 文档 publish_date 范围
```

核心状态只判定：

```text
Qlib provider 新鲜度
announcement / news 文档源行数和映射率
daily_announcement_factor / daily_news_factor 对齐状态
```

覆盖页不再把 `daily_bar`、`adj_factor`、`price_limit` 当作 QDC 每日核心覆盖分数。基础行情是否可用由 Qlib provider 检查给出；QDC 覆盖页主要展示 `announcement`、`news`、后续 `research_report`、`public_sentiment` 等文档源覆盖，以及 `daily_news_factor`、`daily_announcement_factor` 等 external factors 是否按交易日和标的对齐。`news_count`、`announcement_count` 只展示已有明细数量，不把没有事件直接判成缺失。

操作顺序：

```text
1. 切到“覆盖情况”tab，确认 Qlib provider 最新日期、文档源覆盖和 external factor 对齐状态
2. 切到“原始文档预览”或“处理后因子预览”
3. 在标的搜索框输入代码、名称或行业，从下拉里添加一个或多个 instrument
4. 输入开始和结束日期，避免一次拉太多行
```

原始数据预览的典型用途：

```text
news / announcement / 后续 research_report           同一天只显示数量，点击数量展开标题、链接、来源和发布时间
Qlib 基础字段引用                                   只展示抽样状态或引用值，不作为 QDC 采集结果
一张原始文档宽表                                    一行一个日期，横向查看同一天采集到的事件输入
```

原始预览不要直接展示 JSON、raw 文件索引、记录数或缺失统计。上游返回字段可能包含嵌套结构、调试参数和无关字段，对新手不友好，也不利于判断“这些数据后面怎么变成因子”。页面只保留一张按日期聚合的数据宽表，列出因子链路需要的字段：

```text
标的识别：instrument
时间字段：date，一行一个日期
Qlib 基础状态：provider_uri、calendar_date、sample_close、sample_factor
事件明细：news_count、announcement_count，点击数量展开 title、publish_time、url、source
后续扩展：research_report_count、sentiment_count、regulatory_event_count
```

处理后因子预览的输出：

```text
顶部摘要：当前页交易日数量、Qlib 日历对齐天数、当前页新闻明细条数、当前页公告明细条数
因子分类：Qlib 基础字段引用、新闻相关因子、公告相关因子、后续研报/舆情因子、来源追踪
Qlib 标记：带 Qlib 标记的字段会被 external handler 读取；来源追踪和规则说明只用于排查
因子宽表：单标的时每行一个 trade_date；多标的时每行一个 trade_date + instrument，按日期倒序和标的升序排开
分页：按交易日分页，默认使用页面选择的行数作为 page_size；数据量较大的通用表格默认每页展示 5 行并提供上一页/下一页
可展开明细：news_count 和 announcement_count 默认只显示数量，点击数量展开当天多个新闻或公告标题、发布日期和来源
```

宽表是当前最佳处理方式：因子研究的核心动作是横向比较同一交易日的所有字段，而不是把新闻、公告、行情拆成多个小表来回对照。分类卡只负责解释列归属，不打断宽表阅读。

接口边界：

```text
/api/instruments              负责标的下拉搜索，前端加载当前可用标的并连续添加多个选择
/api/raw-instrument-preview   负责按 instrument 读取 raw 留档和 silver 文档表，并转换成原始文档宽表输入
/api/factor-preview           负责按 instrument 合并多个日频 external factor 表，并返回可按交易日展开的文本明细
/api/dataset-preview          保留为兼容接口，不再作为前端主入口
```

## 6. 质量检查页

这个页面用于处理数据异常。

优先级：

```text
open 且 severity 高的问题优先处理
closed 只作历史记录
message 是给人的说明，entity_key 通常指向具体标的或日期
```

## 7. Qlib 接入页

这个页面用于确认 Qlib 基础 provider 是否可用，以及 QDC external factors 是否已经能交给 Qlib handler。

判断顺序：

```text
provider_uri 是否是预期目录
calendars/day.txt 最新日期是否到最近完整交易日
features 中 close / volume / factor 是否存在
抽样 D.features 能否读取 $close / $volume / $factor
QDC external factors 日期范围是否覆盖研究区间
external handler 是否能读取 QDC 因子字段
```

## 8. 后续标的画像页

后续应新增“标的画像”页，作为研究验证视角。

推荐交互：

```text
输入标的 + 日期范围
顶部显示该标的覆盖天数、最早/最晚交易日、新闻/公告数量
主时间线按 trade_date 展示 Qlib 基础字段引用、新闻因子、公告因子
点击某天展开当天新闻标题、公告标题和事件标签
默认只加载最近 250 个交易日，更多历史分页或按日期筛选
```

这个页面不替代总览和回补任务页，因为标的视角看不出整个 dataset 的采集队列是否健康。
