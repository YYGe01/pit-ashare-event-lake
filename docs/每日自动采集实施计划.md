`--crawl-documents` 会在结构化采集后、`build-factors` 前规划并运行默认爬虫源：`cninfo_announcement`、`sse_announcement`、`sina_finance_news`、`eastmoney_roll_news` 和 `nbd_company_news`。如果只想跑单个爬虫源，可加 `--crawl-source-id cninfo_announcement`、`--crawl-source-id sse_announcement`、`--crawl-source-id sina_finance_news`、`--crawl-source-id eastmoney_roll_news` 或 `--crawl-source-id nbd_company_news`。

只使用每日新增数据、不混用历史回补库时，使用 daily-only 隔离配置：

```powershell
qdc --config config/quant_data_center_daily_only.yaml init
qdc --config config/quant_data_center_daily_only.yaml daily-pipeline --symbols "SZ301421,SZ000750,SZ300001,SZ300760"
```

`config/quant_data_center_daily_only.yaml` 会把 DuckDB、raw、Parquet、Qlib provider 和日志全部写到 `data/quant_data_center_daily_only/`。`daily_pipeline` 段保存每日默认参数：`batch_size=50`、`export_start=2026-05-12`、`market_name=all_a_daily`、默认采集公告和新闻文档，并保留跳过步骤开关等。命令行参数会覆盖配置，例如初期固定测试标的必须传 `--symbols "SZ301421,SZ000750,SZ300001,SZ300760"`，临时改批次可传 `--batch-size 20`，临时关闭文档爬虫可传 `--no-crawl-documents`。该模式下不要运行 `plan-backfill` / `run-backfill`；后续有收费源后再用主配置或新的历史库单独做回补。

## 6. 多源候选、存储和并行计划

### 6.1 P0 多源并行容错原则

这个需求合理，并提升为每日采集 P0。原因是免费源不稳定，如果单源阻塞整个全市场采集，数据中心就无法稳定每日滚动。新的默认原则如下：

```text
每个核心 dataset 至少配置 2 个可用 source_id。
同一 dataset 的不同 source_id 在 fetch 阶段并行执行。
每个 source_id 必须有独立超时时间；超时即标记本源本次失败，不等待、不重试到阻塞总流程。
成功源的数据必须先保存 raw/source_object；失败源只记录失败元数据和错误原因。
persist 阶段单写 DuckDB：读取各源 raw/bronze，按 dataset 规则去重、择优、upsert 到 silver。
单个源失败不导致 daily-pipeline 失败；只有所有候选源都失败或核心维度最终无可用数据时，才把该维度标记为 failed/partial。
```

推荐执行拆分：

```text
阶段 1：文档源先落地源级并行、单源 request/source timeout 和 partial-success 口径。
阶段 2：结构化 daily-pipeline 支持 source_ids 配置，并新增 Eastmoney/Sina 结构化备源。
阶段 3：为 daily_bar / adj_factor / price_limit / trade_status 接入 Eastmoney 备源，trade_calendar 接入 Sina 备源。
阶段 4：控制台今日总览展示每个 dataset/字段/source 的失败标的数、成功标的数和超时次数。
```

并发边界：

```text
网络 fetch 可以源级并行。
DuckDB 写入通过短连接和锁等待重试串联落库；后续大规模运行如遇锁竞争，再把 fetch 和 persist 彻底拆开。
raw/documents 目录按 source_id/run_id 隔离，允许并行写不同文件。
同一 source_id 同一日期不要并发跑两份，避免重复请求和重复 raw 包。
```

建议默认超时：

| 类型 | 默认超时 | 说明 |
| --- | ---: | --- |
| 结构化单源单批次 | 60 秒 | 单批 50 个标的以内，超时跳过该源该批次 |
| 公告列表源 | 90 秒 | 包含翻页；PDF 下载另设限制 |
| 公告 PDF 单文件 | 30 秒 | 单 PDF 超时只标记该 PDF 失败，不影响公告 metadata |
| 新闻列表源 | 60 秒 | metadata-only，不抓正文 |
| 因子/同步/导出 | 不按源超时 | 属于本地处理，失败应显式暴露 |

### 6.2 今日总览失败统计口径

今日总览必须从“任务有没有跑完”升级为“每个数据维度、每个源、到底缺了多少标的”。最低展示口径：

```text
date
dataset              daily_bar / adj_factor / price_limit / trade_status / announcement / news
dimension            open / high / low / close / volume / adj_factor / limit_up / limit_down / publish_time / title 等
source_id
expected_instruments 当日参考标的数，例如 all_a active 5515
success_instruments  本源本维度成功覆盖标的数
failed_instruments   expected - success，或源显式失败标的数
timeout_count        本源超时次数
error_count          非超时错误次数
last_error           最近错误摘要
raw_object_count     成功落 raw 的对象数
```

示例解释：

```text
2026-05-12 / daily_bar.open / akshare:
  expected_instruments=5515
  success_instruments=4980
  failed_instruments=535

2026-05-12 / daily_bar.open / backup_source:
  expected_instruments=5515
  success_instruments=5512
  failed_instruments=3

最终 silver daily_bar.open 可用标的数按多源合并后统计，不等同于任何单源成功数。
```

实现上先不要把“无新闻/无公告”当成失败，因为事件型数据天然稀疏。文本源失败统计只统计：

```text
源请求失败/超时
无法解析 publish_time
publish_time 不可信或缺失
标题/URL/标的映射缺失
raw 保存失败
```

### 6.3 文本发布时间归属口径

这个需求合理，并作为硬规则执行：

```text
公告和新闻必须保存 publish_time。
publish_date 必须来自 publish_time，不来自 collect_time。
collect_time 只表示本系统何时采集到。
如果 2026-05-12 发布的公告/新闻在 2026-05-13 才被采集到，silver 仍写 publish_date=2026-05-12。
因子构建按 publish_date 归属到 2026-05-12，不归属到采集日 2026-05-13。
```

对应风险控制：

```text
只有来源给出明确 YYYY-MM-DD 或可可靠转换成 YYYY-MM-DD HH:MM[:SS] 时才入库。
只有“刚刚”“几分钟前”“今天”这类相对时间且无法确定日期时，不进入 silver，只保留 raw 和失败/拒绝原因。
如果源按请求日期返回历史混排，不能再用 crawl_date 强行覆盖 publish_date。
```

`crawl_date` 的新含义：

```text
crawl_date 是采集任务请求/运行分区日期，用于 raw 目录和任务调度。
publish_date 是研究和因子归属日期。
两者允许不同，但必须同时可追踪。
```

### 6.4 多源候选硬门槛

采用硬门槛：

```text
主源或备用源必须能确认今天发布日期。
公告源必须支持按日期查询，或返回字段里有明确 publish_date / disclosure_date。
新闻源必须返回或页面展示完整 YYYY-MM-DD HH:MM[:SS] 发布时间。
只有“刚刚”“今天”“若干分钟前”但无法落到具体日期的候选不采用。
包含历史混排且无法可靠过滤 crawl_date 的候选不采用。
```

### 6.5 存储口径

存储口径：

```text
raw 文件优先保留直观证据：
data/quant_data_center/raw/documents/<date>/<source_id>/<run>/manifest.json
data/quant_data_center/raw/documents/<date>/<source_id>/<run>/records.jsonl

新闻源的 raw JSON 仍保留整页/整包上游响应；用于控制台预览的 records.jsonl 只保存已映射到 instrument 的 normalized metadata 记录。
公告源的 records.jsonl 保存归一化公告列表；PDF 文件另以 source_object 记录 hash、size 和本地 object_id。

DuckDB 继续保存：
crawler_source / crawl_task / crawl_run 控制面
source_object 文件索引
qdc_silver.announcement / qdc_silver.news 规范化结果
daily_news_factor / daily_announcement_factor 因子结果
```

并行抓取执行口径：

```text
不同网站的网络请求可以源级并行。
当前 adapter 在抓取过程中会同时写 raw、bronze、source_object 和 silver；DuckDB 更适合单写，因此必须改为 fetch -> persist 两段。
fetch 阶段并行写各自 raw/documents 文件包；persist 阶段单进程读文件、去重、择优、写 DuckDB。
这是 P0，不再作为“以后优化”处理。
```

去重口径：

```text
raw/documents 保留每个来源的原始记录，不做破坏性去重。
silver 表保留来源级记录，便于排查某个源的缺失或错误。
文本因子构建前按 publish_date + instrument + normalized_title 跨源去重，避免同一新闻/公告被多个来源重复计数。
```

## 7. 自动调度建议

正式调度前先完成小范围真实 smoke。通过后可把每日任务收敛成一个命令：

```powershell
qdc --config config/quant_data_center_daily_only.yaml daily-pipeline
```

如果使用 Windows 计划任务，建议先只做小范围或单日手动验证，再创建正式任务。DuckDB 当前仍按单写进程使用，不要同时跑两个会写同一个 `qdc.duckdb` 的命令；但 `qdc console` 可以在采集过程中保持打开。写入端遇到控制台瞬时只读锁会等待重试，控制台遇到采集写锁会显示“写入中”降级状态并继续刷新。

恢复命令：

```powershell
qdc recover-running --older-than-minutes 60
qdc run-backfill --retry-failed --limit-tasks 20
qdc crawl-recover-running --older-than-minutes 60
qdc crawl-run --retry-failed --limit-tasks 20
```
