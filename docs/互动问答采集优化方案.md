# 互动问答采集优化方案

> 日期：2026-05-15
> 范围：`cninfo_investor_interaction` 前向日更采集。当前免费源不作为历史回采和训练 baseline 依赖。

## 1. 目标

在不使用代理的前提下，把互动问答从“按标的串行慢扫”改为可控的全市场前向日更：

```text
缓存公司标识
源内按标的并发
目标日附近早停
失败标的不中断整批
保留请求、缓存、失败和覆盖指标
```

## 2. 当前瓶颈

互动问答源和公告、新闻、研报不同，它不是全市场按日期查询，而是按标的循环访问：

```text
symbol -> orgId/secid 查询
orgId/secid -> company/question 查询
```

未优化时，每个标的至少 2 次请求；如果按全 A 串行跑，会把大量时间花在重复查询公司标识、无效沪市覆盖、翻页和源级 sleep 上。

## 3. 已实现策略

### 3.1 orgId/secid 本地缓存

缓存文件：

```text
data/quant_data_center/cache/cninfo_investor_interaction_orgs.json
```

日常运行优先读取缓存；只有缓存缺失时才访问 `queryKeyboardInfo`。成功解析的新映射会写回缓存。

缓存已扩展为“公司标识 + 探测状态”，会记录：

```text
org_status
question_status
last_checked_date
last_target_date
latest_provider_publish_date
oldest_provider_publish_date
target_row_count
provider_record_count
page_count
provider_date_counts_json
consecutive_no_data_days
last_latency_ms
last_error
```

这些字段用于后续判断 hot / warm / cold 标的，但默认严格采集模式不会因为 cold 状态跳过每日 page 1 检查。

### 3.2 源内标的并发

新增 CLI 参数：

```powershell
--instrument-parallelism 8
```

这个参数只对类似 `cninfo_investor_interaction` 的按标的循环源有意义。它和 `--parallel-sources` 不同：

```text
parallel-sources       多个 source_id 之间并发
instrument-parallelism 同一个 source_id 内部多个 instrument 并发
```

### 3.3 全市场保护阈值

未传 `--symbols` 时，仍默认只取 `stock_basic` 活跃标的前 50 个，避免误触发全市场长任务。

新增 CLI 参数：

```powershell
--instrument-limit 0
```

`0` 表示显式允许使用所有 active instruments。全市场运行必须显式传这个参数。

### 3.4 日期早停

每个标的按页采集时，如果当前页出现早于目标日的问答日期，则停止继续翻该标的后续页。

这不是历史回采能力，只是防止日更时无边界翻深页。

当前默认每个标的最多扫 2 页；如果命令显式传 `--max-pages`，以命令参数为准。可以用环境变量覆盖默认值：

```text
QDC_INVESTOR_INTERACTION_DEFAULT_MAX_PAGES=1
QDC_INVESTOR_INTERACTION_DEFAULT_MAX_PAGES=all
```

日期扫描状态会区分：

```text
empty_page
older_than_target_date
target_date_exhausted
has_target_date
no_target_date
no_rows
question_failed
```

### 3.5 失败容错

单个标的的 orgId 查询失败或 question 查询失败，会记录到 manifest：

```text
org_failures
question_failures
org_failure_count
question_failure_count
```

失败标的不再导致整个 `crawl-daily` 任务失败，后续可按 manifest 或任务结果评估是否补跑。

### 3.6 连接复用

互动问答源使用每线程 `requests.Session()` 复用 HTTP 连接。单元测试可通过环境变量禁用 session：

```text
QDC_INVESTOR_INTERACTION_DISABLE_SESSION=1
```

## 4. 推荐命令

小样本 smoke：

```powershell
qdc crawl-daily --date 2026-05-14 --source-id cninfo_investor_interaction --symbols "SZ002594,SZ000001" --page-size 50 --max-pages 2 --instrument-parallelism 4 --force
```

默认保护阈值 50 个标的：

```powershell
qdc crawl-daily --date 2026-05-14 --source-id cninfo_investor_interaction --page-size 50 --instrument-parallelism 8 --force
```

显式全 active instruments：

```powershell
qdc crawl-daily --date 2026-05-14 --source-id cninfo_investor_interaction --page-size 50 --instrument-parallelism 8 --instrument-limit 0 --source-timeout-seconds 7200 --force
```

如果需要更谨慎，可以先用 300 / 1000 个标的测吞吐：

```powershell
qdc crawl-daily --date 2026-05-14 --source-id cninfo_investor_interaction --page-size 50 --max-pages 2 --instrument-parallelism 8 --instrument-limit 300 --source-timeout-seconds 1800 --force
```

## 5. 运行参数建议

默认建议：

```text
page_size: 50
max_pages: 默认 2；若只想做最快 page 1 探测，显式传 1
instrument_parallelism: 8
request_timeout_seconds: 15-30
source_timeout_seconds: 1800-7200
```

如果 429、403、连接重置或超时明显增加，先降低：

```text
instrument_parallelism: 4
page_size: 30
max_pages: 1
```

## 6. 不用代理的耗时评估方法

先跑 20、50、100 个标的，记录：

```text
elapsed_seconds
instrument_count
request_count
org_cache_hit_count
org_cache_update_count
org_failure_count
question_failure_count
provider_record_count
mapped_record_count
```

全市场耗时估算：

```text
estimated_seconds = sample_elapsed_seconds / sample_instrument_count * active_instrument_count
```

如果 orgId 缓存还没建好，首次全市场会更慢；第二次以后应主要只剩 question 请求。

## 7. 2026-05-15 本机样本耗时

本机 `qdc_silver.stock_basic` 活跃标的数：

```text
5515
```

测试条件：

```text
不用代理
date: 2026-05-14
page_size: 50
max_pages: 1
instrument_parallelism: 8
request_timeout_seconds: 20
source_timeout_seconds: 300 / 600
样本：按本地 stock_basic 取 SZ / SH / BJ 混合标的
```

实测结果：

| 样本 | orgId 缓存状态 | request_count | 耗时 |
| --- | --- | ---: | ---: |
| 20 个混合标的 | 冷启动，缓存命中 0，更新 20 | 40 | 35.39 秒 |
| 同 20 个混合标的 | 缓存命中 20，更新 0 | 20 | 21.99-25.07 秒 |
| 50 个混合标的 | 部分冷启动，缓存命中 20，更新 30 | 80 | 65.56 秒 |
| 同 50 个混合标的 | 缓存命中 50，更新 0 | 50 | 44.60 秒 |
| 同 50 个混合标的 | 缓存命中 50，`instrument_parallelism=12` | 50 | 44.79 秒 |

按 50 个缓存命中样本估算，全市场 5515 个 active instruments 的日更耗时约：

```text
44.60 / 50 * 5515 = 4919 秒，约 82 分钟
```

首次冷启动需要额外建立 orgId 缓存。按 20 个冷启动样本和 50 个部分冷启动样本综合估算，首次全市场大约：

```text
2.0-2.7 小时
```

并发从 8 提到 12 没有明显改善，说明当前瓶颈主要不是 worker 数，而是接口响应时间、单请求处理和上游吞吐。后续优先优化方向应是缓存覆盖率、减少翻页和减少无效标的请求，而不是继续盲目提高并发。

## 8. 2026-05-15 二次优化后样本耗时

二次优化内容：

```text
缓存扩展为 orgId/secid + 探测状态。
任务结果输出 target_date_instrument_count 和 instrument_status_counts。
每线程复用 requests.Session。
默认每个标的最多扫 2 页，显式 --max-pages 可覆盖。
```

实测结果：

| 样本 | max_pages | 缓存状态 | request_count | 命中目标日标的 | 耗时 |
| --- | ---: | --- | ---: | ---: | ---: |
| 50 个混合标的 | 1 | org 缓存命中 50 | 50 | 9 | 31.73 秒 |
| 50 个混合标的 | 默认 2 | org 缓存命中 50 | 52 | 9 | 39.46 秒 |
| 100 个混合标的 | 1 | org 缓存命中 100 | 100 | 19 | 57.47 秒 |
| 100 个混合标的 | 默认 2 | org 缓存命中 100 | 103 | 19 | 68.08 秒 |

按 100 个缓存命中样本估算，全市场 5515 个 active instruments：

```text
page 1 探测：57.47 / 100 * 5515 = 3169 秒，约 53 分钟
默认 2 页：68.08 / 100 * 5515 = 3755 秒，约 63 分钟
```

和上一轮 50 个缓存命中样本估算的约 82 分钟相比，当前严格覆盖模式下的预期日更时间下降到约 53-63 分钟。这个估算仍然不使用代理，不跳过冷门标的。

## 9. 训练注意

互动问答仍然是前向可选源，不作为训练 baseline。若未来做实验因子，必须额外处理：

```text
覆盖标记
采集失败标记
真实 0 和未采集区分
固定起始日之后的数据一致性
```
